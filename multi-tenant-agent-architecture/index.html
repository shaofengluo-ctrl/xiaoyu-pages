    多租户 Agent 服务化架构方案¶

    创建时间：2026-03-15 状态：规划阶段 目标：将 opencode + MCP 从单机单用户模式，改造为多人多群聊共享的远端服务

    1. 问题背景¶

    当前架构：每个飞书群聊 session 都在本机拉起一个完整的 opencode 进程 + 所有 MCP 子进程。多人同时使用时本机会被拖死。

    核心需求： - 一个用户一个 session，一个群聊一个 session - 群聊空闲时杀掉 session，agent 不再响应 - MCP 共享，不再每个 session 起独立进程 - SAP 凭据分级：只读用服务账号，写入由用户自行提供

    2. 关键发现（2026-03-15 调研）¶

    2.1 opencode serve 已有完整 HTTP API¶

    opencode 源码（anomalyco/opencode，TypeScript/Bun 项目）的 opencode serve 模式已经是一个完整的 REST API 服务器：

    能力 状态 端点
    多 session CRUD ✅ GET/POST/DELETE /session
    异步发消息 ✅ POST /session/:id/prompt_async（返回 204）
    SSE 事件流 ✅ GET /event 推送所有状态变化
    MCP 管理 ✅ /mcp 路由可动态连接/断开
    Basic Auth ✅ OPENCODE_SERVER_PASSWORD 环境变量
    多项目目录 ✅ x-opencode-directory header 隔离
    OpenAPI spec ✅ /doc 自动生成

    结论：不需要自建 Session Manager，直接在 opencode serve 上面搭消息网关。

    2.2 MCP 进程是 Instance 级共享的¶

    opencode 里 MCP 进程按 Instance（项目目录）共享，不是按 session。同一项目目录下的所有 session 共用一套 MCP 连接。

    这正好满足需求——多个群聊 session 共享同一个 sap-mcp 实例，不会每个 session 起一个新进程。

    2.3 SAP 凭据分离的安全底线¶

    S_DEVELOP 授权对象的 ACTVT 字段：

    ACTVT 含义 服务账号可授 说明
    03 显示（只读） ✅ 安全 getObjectSource, searchObject, runQuery(SELECT)
    02 修改 ❌ 破坏审计追溯 setObjectSource, lock
    01 创建 ❌ 破坏 TR 归属 createObject

    写操作必须用个人账号，否则 SAP 系统的变更日志全部记在服务账号名下，无法追责。

    2.4 abap-adt-api 底层支持动态 token¶

    marcellourbani/abap-adt-api 的 ADTClient 构造函数支持 BearerFetcher 回调，可以实现按请求动态获取 OAuth token。当前 MCP wrapper 没用这个能力，但改造基础存在。

    2.5 飞书 Bot 推荐用 WebSocket 而非 Webhook¶

    WebSocket 长连接不需要暴露公网 IP，更安全。chat_id 做 session 路由主键，open_id 做用户识别。

    4. 各层详细设计¶

    4.1 消息网关（Gateway）¶

    职责：飞书消息 ↔ opencode serve 的桥接层。

    • 飞书侧：注册企业自建应用，开启「机器人」能力，用 WebSocket 长连接订阅 im.message.receive_v1 事件
    • 路由规则：chat_id（群聊 ID）→ 映射到一个 opencode session
    • 用户识别：从飞书事件提取 open_id，关联到该用户的 SAP 凭据
    • 消息转发：
    • 飞书消息 → POST /session/:id/prompt_async
    • opencode SSE 事件 → 解析 part.delta → 飞书 Bot 回复
    • 实现：轻量 Node.js/Python 服务，无状态，可水平扩展

    4.2 空闲回收规则¶

    消息网关维护 chat_id → {session_id, last_active, has_pending_tasks} 映射。

    层级 条件 动作
    温和空闲 15 分钟无消息 内存中标记 idle，不做动作
    警告 30 分钟无消息 向群聊发消息："我先休息了，有事再叫我"
    回收 45 分钟无消息（或警告后 15 分钟无响应） DELETE /session/:id，释放资源
    强制回收 单 session 累计存活超 4 小时 无论是否活跃，强制回收（防止内存泄漏）
    异常回收 session 进程 OOM / 崩溃 立即回收，下次消息自动重建

    额外信号（不仅看"最后一条消息"）： - 有 pending background task → 不算空闲，延长超时 - 有未完成 todo → 发警告时提示用户"还有未完成任务" - session context 占用超阈值 → 触发 compact 而非回收

    优雅关闭（Drain and Save）： 1. 停止接受新输入 2. 等 in-flight LLM 请求完成（或超时切断） 3. 序列化状态（opencode 本身存 SQLite，天然持久化） 4. 销毁 session 对象

    "有事再叫我"后收到消息： - session 还在（30-45min 窗口）→ 直接复用 - session 已销毁 → 自动创建新 session，用户无感

    4.3 sap-mcp 凭据双轨改造¶

    systems.json 改造¶

    // 改造前：每个系统包含 user/password
{
  "systems": {
    "s4d": {
      "client": "130",
      "password": "example-s4d-password"
    }
  }
}

// 改造后：只保留系统连接信息 + 只读服务账号
{
  "systems": {
    "s4d": {
      "client": "130",
      "adt_url": "https://mis4d.mioffice.cn",
      "service_account": {
        "user": "SVC_MCP_READONLY",
        "password": "encrypted:xxxxx"
      }
    }
  }
}

    操作分级¶

    操作类型 凭据来源 示例工具
    只读 统一服务账号（预配置在服务端） getObjectSource, searchObject, runQuery(SELECT), objectStructure, classIncludes, usageReferences
    写入 用户自行提供，session 级别绑定 setObjectSource, lock, createObject, activateObjects
    危险 禁止（Hard Block 不变） deleteObject, transportRelease, DML SQL

    ConnectionPool 改造方向¶

    // 双轨模式：有用户凭据用用户的，没有就用服务账号
private createEntry(systemId: string, credentials?: UserCredentials): PoolEntry {
  const config = this.systemManager.getSystemResolved(systemId);

  const user = credentials?.user ?? config.service_account.user;
  const password = credentials?.password ?? config.service_account.password;

  const client = new ADTClient(config.url, user, password, config.client, config.language);
  client.stateful = session_types.stateless;
  // ...
}

    用户凭据获取流程¶

    1. 用户首次在群聊中要求写操作
    2. Agent 回复："写操作需要你的 SAP 账号。请私聊发给我：系统/用户/密码"
    3. 用户通过飞书私聊（非群聊！）发送凭据
    4. Gateway 将凭据加密存入 session 上下文（内存，不落盘）
    5. session 销毁时凭据随之消失

    安全措施¶

    措施 说明
    凭据不落盘 仅存在 session 内存中，进程死亡即清除
    私聊传输 不在群聊中暴露密码
    会话级有效 session 回收后需重新提供
    加密存储 内存中用 AES 加密，不明文持有
    审计日志 所有写操作记录：谁、什么时候、改了什么（不记录密码）

    4.4 MCP 共享模式补充¶

    当前 sap-mcp 用 stdio 模式，由 opencode 作为子进程启动。在共享架构下有两个选择：

    方案 A：保持 stdio，由 opencode Instance 管理（推荐起步） - 不改 sap-mcp 的 transport 层 - opencode 的 Instance 机制已经天然共享 MCP 进程 - 凭据分级在 sap-mcp 内部实现（ConnectionPool 双轨） - 优点：改动最小 - 缺点：凭据传递需要通过 MCP 工具参数（如 switchSystem 增加 credentials 参数）

    方案 B：改为 Streamable HTTP，独立部署 - sap-mcp 从 StdioTransport → NodeStreamableHTTPServerTransport - 凭据通过 HTTP header 传递（Authorization: Basic xxx 或自定义 header） - 按 MCP session 维护独立的 ADTClient 连接池 - 优点：完全解耦，可独立扩展 - 缺点：改动大，需要处理 MCP session 管理

    建议：先用方案 A 验证整体流程，再根据需要升级到方案 B。

    5. 需要开发的组件¶

    组件 工作量 优先级 说明
    消息网关 中 P0 飞书 WebSocket 事件 → opencode REST API 桥接
    空闲回收逻辑（在网关中） 小 P0 定时器 + session 生命周期管理
    sap-mcp 凭据分级改造 中 P1 服务账号(只读) + 用户凭据(写入)双轨
    凭据收集流程 小 P1 飞书私聊 → 加密 → 注入 session
    SAP 只读服务账号申请 小 P1 向 Basis 团队申请 SVC_MCP_READONLY
    飞书 Bot 注册 小 P0 企业自建应用 + WebSocket 事件订阅
    远端部署脚本 小 P2 opencode serve + PM2 + 反代
    监控/告警 中 P2 session 数量、内存、SAP 连接数

    6. 关键风险¶

    风险 影响 缓解
    SAP 并发连接数限制 SAP 对同一用户有 session 数限制（通常 6 个） 服务账号用 stateless 模式，不占 SAP session
    opencode serve 稳定性 长时间多 session 运行的内存/稳定性未经验证 PM2 守护 + 定期重启 + session 强制回收
    凭据泄露 用户密码在传输/存储中被截获 私聊传输 + 内存加密 + 不落盘 + session 级生命周期
    资源膨胀 大量群聊同时活跃 硬性上限（如最多 20 并发 session）+ 空闲回收
    飞书消息格式 飞书富文本/图片 ↔ 纯文本 agent 的转换 网关层做格式转换，图片转 base64 或 URL

    7. 里程碑¶

    M1：最小可用（MVP）¶

    • 飞书 Bot 注册 + WebSocket 事件订阅
    • 消息网关：chat_id → session 映射 + 消息转发
    • opencode serve 远端部署
    • sap-mcp 保持 stdio，暂不改造凭据（用当前 systems.json）
    • 验证：一个群聊能正常对话

    M2：多群聊 + 空闲回收¶

    • 多群聊同时工作
    • 空闲回收机制上线
    • 并发 session 数限制

    M3：凭据分级¶

    • SAP 只读服务账号上线
    • sap-mcp ConnectionPool 双轨改造
    • 飞书私聊凭据收集流程
    • 写操作凭据验证
