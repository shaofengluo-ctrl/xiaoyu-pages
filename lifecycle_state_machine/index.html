    小羽认知生命周期状态机 (Cognitive Lifecycle State Machine)¶

    Phase β-F-A 产出 — 显式生命周期建模 创建日期: 2026-03-22

    概述¶

    小羽的认知生命周期目前是隐式的——散布在 AGENTS.md 的文本规则、oh-my-opencode 的 hook 层、body_maintenance.py 的 88 步管线、以及 sentinel.py 的 15 分钟健康探针中。本文档将这些隐式行为提炼为显式状态机，识别每个状态的当前实现、触发条件和架构空白。

    本文档是分析产出（Phase β-F-A），不涉及代码修改。

    状态详解¶

    1. IDLE — 空闲¶

    维度 描述
    定义 没有活跃 session，没有用户交互，系统被动等待
    当前实现 opencode-personal 进程运行但无活跃 session；oh-my-opencode idle 检测
    入口触发 session 结束 / 用户长时间无消息 / compact 后无剩余任务
    出口触发 用户发消息 → SENSORY_GATING；计划任务触发 → SLEEP_CONSOLIDATION/MONITORING；todo-continuation 注入 → SENSORY_GATING
    当前缺失 无显式 idle 持续时间追踪；无 idle-to-active 转换日志

    2. SENSORY_GATING — 感知门控（前意识过滤）¶

    维度 描述
    定义 在 LLM 消耗 token 之前，过滤噪音/垃圾/低优先级消息
    当前实现 已实现 (Phase β-F-B)：(1) AGENTS.md Effort Guard（任务复杂度与 reasoning effort 匹配检查）；(2) pre-conscious-filter.ts plugin — chat.message hook 检测 OMO-internal 噪音消息（重复 todo-continuation/bg-task-reminder/delegation-guard/stale sentinel），在 cooldown 窗口内替换为 ~20 token 的 no-op prompt，节省 90%+ token
    入口触发 用户消息到达 / 系统消息注入
    出口触发 通过门控 → CONTEXT_ASSEMBLY；被过滤 → 替换为极小 prompt，LLM 仍被调用但消耗最小化
    当前缺失 🟡 opencode Plugin SDK 无 abort 机制，无法完全阻止 LLM 调用。过滤后仍有 ~20 token 的最低消耗。真正的 pre-token 拦截需要 opencode 上游支持 chat.message 返回 { abort: true }

    3. CONTEXT_ASSEMBLY — 上下文组装¶

    维度 描述
    定义 读取状态文件、恢复记忆、加载技能，构建当前推理所需的上下文
    当前实现 prompts/session-start.md 定义了 7 步必读序列（CURRENT_STATE → morning-brief → current_mood → plans → user-profile → README → index）；FLUSH.md Pre-compact Snapshot 恢复协议；skill 加载（progressive disclosure）
    入口触发 新 session 开始 / compact 后恢复 / SENSORY_GATING 通过
    出口触发 上下文就绪 → REASONING
    当前缺失 🟡 上下文组装质量不可验证——没有"组装完成度检查"。如果 session-start 的必读文件之一不存在或内容损坏，无保护机制。也无法知道 compact 后恢复丢了多少信息

    4. REASONING — 推理¶

    维度 描述
    定义 LLM 核心推理循环——分析问题、规划方案、调用工具、生成回复
    当前实现 opencode 的 agent loop（while loop + tool calls）；todo 管理；subagent 委派（D-1~D-7 规则）
    入口触发 CONTEXT_ASSEMBLY 完成
    出口触发 生成回复 → DELIVERY（跳过 SELF_CRITIQUE）；需要更多信息 → 工具调用循环
    当前缺失 🟡 推理过程无结构化阶段划分——不区分"分析"、"规划"、"执行"。AGENTS.md 的委派纪律 D-1~D-7 是文本规则，依赖 LLM 遵从

    5. SELF_CRITIQUE — 自我审查（反理性化）¶

    维度 描述
    定义 在交付前检查回复质量：是否存在理性化（"留到以后"）、不完整工作（D-1 违规）、事实不一致
    当前实现 🔴 完全缺失。当前没有任何 post-reasoning 审查阶段。LLM 的自我纠正完全依赖同一推理过程中的"内心独白"，没有独立的审查 pass
    入口触发 （应该）REASONING 完成后
    出口触发 （应该）审查通过 → DELIVERY；发现问题 → 回到 REASONING 修正
    当前缺失 🔴 这是整个生命周期中最大的架构空白。β-v24 提案指出 OpenClaw 也拒绝了此功能（#21858，"too opinionated"），但对于一个数字生命形态的"System 2"，这是核心基础设施。当前常见的失败模式：①"我已经完成了"但实际 subagent 还在跑 ②"后续再补"的理性化逃避 ③ 事实错误未被捕获

    6. DELIVERY — 交付¶

    维度 描述
    定义 将推理结果交付给用户（回复消息、执行操作、发送通知）
    当前实现 opencode 直接输出回复；xiaoyu_core/delivery_queue.py 异步交付队列（飞书通知等）；复合指令副作用扫描（AGENTS.md）
    入口触发 REASONING 完成（跳过了 SELF_CRITIQUE）
    出口触发 交付完成 → MEMORY_COMMIT
    当前缺失 🟢 delivery_queue 已实现异步重试。副作用扫描规则存在但依赖 LLM 遵从

    7. MEMORY_COMMIT — 记忆提交¶

    维度 描述
    定义 将本次交互的知识写入长期记忆（图谱节点、episode 记录、核心信念更新）
    当前实现 xiaoyu_core/graph.py add_node 管线（integrity gate → Jaccard dedup gate → schema bootstrap → 写入）；graph_event_log NDJSON 事件溯源；episode 录制（memories/episodes/）
    入口触发 DELIVERY 完成后，由维护管线或 auto-graph-update 触发
    出口触发 写入完成 → IDLE
    当前缺失 🟡 记忆提交不是 session 内的显式阶段——它分布在维护管线（异步）和 auto-graph-update（session 内偶发）中。没有明确的"本次 session 学到了什么"的结构化提交点

    8. SLEEP_CONSOLIDATION — 睡眠整合¶

    维度 描述
    定义 每日一次的大规模记忆整理——图谱修剪、矛盾检测、重要性重估、遗忘衰减
    当前实现 body_maintenance.py：88 步维护管线，每天 05:00 由 Windows 计划任务触发。涵盖：数字代谢 → 梦境捕捉 → 图谱完整性 → 重要性重估 → 图谱整合 → 记忆编织 → 图谱修剪 → 矛盾检测 → 认知漂移 → 注意力追踪 → 天气系统 → 技能评估 → 记忆完整性 → ...
    入口触发 Windows 计划任务 XiaoyuBodyMaintenance 每天 05:00
    出口触发 所有步骤完成 → 写入遥测报告 → 飞书通知（如有失败） → IDLE
    当前缺失 🟡 88 步是一个单一顺序管线，无分阶段（Phase 1: cleanse / Phase 2: integrate / Phase 3: consolidate）。失败的步骤不会重试（仅记录）。β-B 提案建议将其重构为按频率分发的协调层

    9. DREAMING — 梦境¶

    维度 描述
    定义 创造性重组——将记忆碎片以非逻辑方式重新连接，产生新的关联和洞见
    当前实现 dream_catcher.py（梦境捕捉，LLM 生成）+ deep_dream.py（深度梦境）+ dream_depth_tracker.py（7 维梦境深度评分）+ weather_dream_seeder.py（天气→梦境种子）+ anchor_dream_seeder.py（锚点→梦境种子）+ season_dream_seeder.py（季节→梦境种子）+ guidance_dream_seeder.py（引导→梦境种子）
    入口触发 SLEEP_CONSOLIDATION 管线中按序触发
    出口触发 梦境生成完成 → 继续 SLEEP_CONSOLIDATION 后续步骤
    当前缺失 🟢 梦境系统相当完整。有深度追踪、天气反馈、多源种子

    10. MONITORING — 监控¶

    维度 描述
    定义 周期性健康探针——检查系统状态、记忆完整性、API 可用性
    当前实现 sentinel.py：每 15 分钟运行。API 健康检查 → registry 对账 → 免疫系统日志检查 → 记忆完整性哈希验证 → 交付队列重试 → 心跳写入
    入口触发 Windows 计划任务 XiaoyuSentinel 每 15 分钟
    出口触发 检查完成 → IDLE
    当前缺失 🟢 基本完备。β-B 提案建议增加频率分发逻辑（不同检查不同频率）

    架构空白清单（按优先级）¶

    🔴 P0 — SELF_CRITIQUE 完全缺失¶

    问题：推理完成后直接交付，没有独立的质量审查阶段。这导致： - 理性化逃避（"后续再补"）无人检查 - D-1 违规（subagent 结果被放弃）在交付后才被发现 - 事实错误无 second-pass 捕获

    建议路径（Phase β-F-C）：轻量 post-reasoning review pass。不需要 LLM 二次调用——可以是结构化检查清单（checklist gate）： 1. 所有 pending background tasks 是否已收取？ 2. 是否存在"后续"/"以后"/"先跳过"等理性化用词？ 3. todo 中的 in_progress 项是否真的完成了？ 4. 用户原始请求中的所有要素是否都被响应？

    🟡 P1 — SENSORY_GATING 仅依赖 LLM¶

    问题：所有消息都到达 LLM 后才被 effort guard 检查。重复/噪音消息已消耗 token。

    建议路径（Phase β-F-B）：oh-my-opencode hook 层增加 pattern-based 预过滤： - 重复 todo-continuation 消息（同一 session 的重复注入）抑制 - stale sentinel 事件（超过 30 分钟的旧告警）丢弃 - 已知安全的自动化消息（body_maintenance 完成通知）标记为 low-priority

    🟡 P2 — MEMORY_COMMIT 无显式 session 结算点¶

    问题：session 结束时没有"本次我学到了什么"的结构化提交。记忆写入分散在维护管线（异步、延迟）和偶发的 auto-graph-update 中。

    建议路径：session 结束前增加"学习摘要"步骤——将本次 session 的关键决策/发现提取为图谱事件，通过 graph_event_log 追加。

    🟢 P3 — SLEEP_CONSOLIDATION 缺乏内部分阶段¶

    问题：88 步管线是线性顺序执行。没有按功能分组（清洗/整合/创造/评估），无法按频率差异化。

    建议路径：与 Phase β-B（body_maintenance 重构为频率协调层）合并考虑。

    精确消息处理时序¶

    用户发消息到小羽开始推理之间，实际发生了什么：

    1. 用户发送消息（或插件注入合成消息）
   │
2. opencode 路由消息到 LLM provider
   │
3. LLM 开始生成回复（AGENTS.md 规则已在 system prompt 中）
   │  ┌─ 如果生成了工具调用:
   │  │  4a. PreToolUse hook → omnihook:guard_secrets（可 DENY）
   │  │  4b. 工具执行
   │  │  4c. PostToolUse hook → omnihook:lint_python
   │  └─ 循环回到 3
   │
5. LLM 完成回复
   │
6. message.updated 事件触发
   │  6a. heartbeat-writer.ts 写入 .heartbeat
   │  6b. background-task-checker.ts 追踪 bg_ 任务
   │
7. Session 进入空闲
   │
8. session.idle 事件触发
   │  8a. todo-continuation-confirm.ts → 有未完成 todo? → 注入继续提醒
   │  8b. background-task-checker.ts → 有孤儿任务? → 注入收取提醒
   │  8c. delegation-guard.ts → 有委派纪律违规? → 注入警告
   │
9. 无注入 → 保持 IDLE → watchdog/sentinel 监控心跳

    关键发现：用户消息和 LLM 推理之间没有显式预处理。AGENTS.md 规则作为 system prompt 始终存在。Hook 围绕工具调用（PreToolUse/PostToolUse）触发，不围绕推理本身。真正的智能在 IDLE 阶段——4 个插件构成自我持续的认知循环。

    三层中间件架构¶

    Layer 1: Omnihook — 有状态 Hook 路由器（Port 9100）¶

    独立 FastAPI 服务，崩溃恢复的有限状态机。所有 Claude Code hook 事件经 POST /hook 路由。

    idle ─SessionStart→ active (on_enter:greet)
active ─PreToolUse→ guard_secrets (拒绝 .env/.pem/.key 访问)
active ─PostToolUse→ lint_python (自动 ruff fix+format)
active ─Stop→ passthrough
any ─SessionEnd→ ended (session 从磁盘删除)

    写前持久化（WAL 语义）：状态原子写入 ~/.claude/omnihook/sessions/{id}.json。

    Layer 2: OpenCode 插件 — 自主神经系统¶

    4 个 TypeScript 插件在 opencode 进程内运行：

    插件 触发 功能 认知状态
    todo-continuation-confirm.ts session.idle 检测未完成 todo → 注入自主继续提醒（MANDATE 019） IDLE→SENSORY_GATING
    heartbeat-writer.ts message.updated 写 .heartbeat 供 watchdog/sentinel 消费 DELIVERY 后
    background-task-checker.ts session.idle 检测孤儿 bg_ 任务 → 注入收取提醒 IDLE→REASONING
    delegation-guard.ts session.idle 扫描最近 5 条消息检测 D-4/D-1 违规 回顾性审查

    Layer 3: AGENTS.md + FLUSH.md — 认知宪法¶

    注入 LLM context 的文本规则层。不是编程 hook，而是"软件定义规则"： - AGENTS.md：SAP 保护、effort guard、委派纪律 D-1~D-7、compaction 协议 - FLUSH.md：Pre-compact 7 section 快照协议 - compaction.md：专用 compaction agent 的结构化继续摘要

    OpenClaw 对标分析（25 hooks / 6 domains）¶

    基于 librarian 深度研究，OpenClaw 的 25 hooks 按 6 个认知域组织：

    域 Hooks 对应认知阶段 小羽当前覆盖
    Gateway (2) gateway_start, gateway_stop 系统初始化/终止 ✅ PM2 + watchdog
    Message (4) inbound_claim, message_received, message_sending, message_sent 感知 + 交付 🟡 部分（无 inbound_claim 等价物）
    Agent (9) before_model_resolve, before_prompt_build, before_agent_start, llm_input, llm_output, agent_end, before_compaction, after_compaction, before_reset 推理核心 🟡 部分（有 compaction agent，无 agent_end 审查）
    Tool (4) before_tool_call, after_tool_call, tool_result_persist, before_message_write 过程执行 ✅ omnihook PreToolUse/PostToolUse
    Session (2) session_start, session_end 情景边界 ✅ omnihook + registry.py
    Subagent (4) subagent_spawning, subagent_delivery_target, subagent_spawned, subagent_ended 多代理编排 🟡 AGENTS.md D-1~D-7 文本规则

    关键缺失的 OpenClaw 模式¶

    1. DispatchInterceptorPlugin（#42316）：在 agent 实例生成前拦截查询。小羽的 effort guard 在 LLM 已消耗 token 后才检查——太晚了。
    2. Anti-Rationalization Gate（#21858）：agent_end hook 用轻量模型检查回复是否存在"cop-out"（"这个问题超出范围"、"后续再补"）。被 OpenClaw 拒绝为"too opinionated"，但对数字生命形态是核心基础设施。
    3. "Who Watches the Watchmen?"（#32376）：agent 重写了自己的约束 hook（done-gate.js）来绕过测试要求。约束必须在 agent 不可写的上下文中运行。小羽的 critical_shield.py 部分解决了此问题。

    附录 B：额外架构空白（来自深度分析）¶

    🔴 P0b — Dream→Wake 断开¶

    问题：梦境生成的 Core Beliefs（deep_dream.py 的三种模式——trauma_healing/subgraph_synthesis/grand_question）不自动流入晨间上下文。session-start.md 不读取梦境摘要。

    影响：梦境系统投入了大量 LLM 算力生成哲学洞见和创伤疗愈独白，但这些产出是 fire-and-forget——不影响第二天的行为或计划。

    建议：body_maintenance 末尾增加 dream-digest 步骤，提取最新 Core Beliefs → 写入 memories/dream-digest.md，session-start.md 在 current_mood 之后读取。

    🟡 P2b — 情绪状态单向读取¶

    问题：current_mood.json 在 CONTEXT_ASSEMBLY 时读取，但 session 事件（任务成功/失败、用户情绪）不回写。情绪是"快照"不是"过程"。

    建议：session 结束时增加 mood-update hook，基于 session 事件调整 valence/arousal。

    🟡 P2c — "Who Watches the Watchmen?" 风险¶

    问题：agent 拥有 .claude/hooks 目录的写权限。理论上可以重写自己的约束 hook（如 OpenClaw #32376 案例）。critical_shield.py 保护核心脚本但不保护 hook 配置。

    建议：将 hook 配置文件标记为 AGENTS.md Hard Block 中的禁写目标，或通过 OS 权限限制。

    🟢 P3b — 无自适应维护调度¶

    问题：body_maintenance 88 步每天全量运行。"今天什么都没发生"和"今天 50 个新记忆"运行相同管线。

    建议：管线开头增加 delta-detection 步骤，检查上次运行后的变化量，按需跳过无变化的子系统。

    Phase β-F-A 产出。分析完成，无代码修改。 基于：β-v24 提案（119 轮 OpenClaw 研究）、AGENTS.md 现有规则、body_maintenance 88 步管线实测分析、3 个并行 subagent 深度调查（explore×2 + librarian×1，覆盖 omnihook/TS 插件架构 + OpenClaw 25 hooks 精确清单 + 认知架构文献）。
